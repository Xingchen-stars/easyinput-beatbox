## 一、我选择了什么项目

这次我选择复刻课程里的案例 2——EasyInput Beatbox。它使用 EasyInput V2.0 开发板和 ESP32-S3 芯片，可以把八键键盘变成一台能够独立发声和走拍的鼓机。板子负责节拍、声音和实体按键，电脑网页负责显示状态、编辑 Pattern 和同步操作。

我对这个项目最直观的理解是：**板子是真正的鼓机，网页只是它的显示器和编辑器。** 即使电脑端页面出现卡顿，也不应该影响板子本身继续发声和走拍。

我的目标分成两步：

1. 先把老师提供的原版项目完整编译、烧录并运行起来；
2. 在不破坏原版鼓机功能的前提下，增加一个和我自己的使用习惯有关的小改造。

## 二、原版复刻过程

我先查看了课程资料和开源仓库，确认项目包含 ESP32 固件、网页应用、桌面封装和协议文档，不是一个只有界面的演示项目。之后按照下面的主线完成复刻：

1. 准备 Git、Node.js、pnpm、Chrome/Edge 和 ESP-IDF 开发环境；
2. 获取 `Zhaohan-Wang/easyinput-beatbox` 项目代码；
3. 使用 ESP-IDF 5.5.5，把固件目标设置为 `esp32s3` 并完成编译；
4. 板子开机状态下短按一次 BOOT，确认出现下载端口后烧录固件；
5. 烧录结束后给板子断电，再重新开机，让它退出下载模式并正常运行；
6. 安装网页依赖并启动本地页面，在 Chrome/Edge 中通过 Web Serial 连接开发板；
7. 先验收原版，再开始修改。

这一步让我理解了课程里“分阶段验收”的意义。编译成功只能说明代码生成了固件；烧录成功也不能直接说明功能正确。还要继续检查板子能否开机、能否发声、按键是否正确、网页能否同步。

## 三、原版运行结果

原版跑通后，我在实物上逐项测试了以下功能：

- 板子可以正常开机，扬声器能够播放节拍和鼓音；
- 八个实体按键都能正常响应；
- 鼓垫按下后有声音，网页对应位置也会亮起；
- 旋钮可以调节 BPM，播放和停止可以正常控制；
- 网页可以连接开发板，并接收板端返回的状态；
- 网页和实体操作能够互相同步。

这些现象是我在真实开发板上看到和听到的，不是只根据代码或测试脚本推测出来的。

## 四、我的主要改造：三档有声速度预设

### 1. 改造前

原版主要通过旋转编码器连续增加或减少 BPM。这个方式很自由，但在练习时，如果我经常需要在慢速、正常速度和快速之间切换，就要转很多次旋钮或者在网页中手动输入数值。

### 2. 为什么要改

我希望它更像一个练习工具：

- 刚开始练习时使用 90 BPM；
- 按原版速度练习时使用 120 BPM；
- 熟悉以后提高到 140 BPM。

另外，操作实体旋钮时我不想一直盯着网页，所以希望板子能够直接播报当前选中的速度档位。

### 3. 改造后

我增加了三个固定速度：

| 档位名称 | BPM | 使用场景 |
| --- | ---: | --- |
| 慢速练习 | 90 | 刚开始练习，方便跟上节奏 |
| 原版 | 120 | 保持老师项目的默认速度 |
| 快速节奏 | 140 | 熟悉以后提高练习难度 |

网页 BPM 控制旁增加了三个快捷按钮。点击按钮后，BPM 会立即切换到对应数值。

实体旋钮也增加了相同的操作逻辑：

1. 快速双击旋钮，进入速度选择模式；
2. 旋转旋钮，在 90、120、140 三档之间循环选择；
3. 每次切换时，板子语音播报“慢速练习”“原版”或“快速节奏”；
4. 短按旋钮确认；
5. 确认后板端 BPM 和网页 BPM 一起更新；
6. 5 秒没有继续操作就自动退出，不改变当前速度。

为了不破坏原来的操作，正常旋转仍然可以连续微调 60～240 BPM；单击仍然控制播放和停止。因为程序要判断用户是在单击还是双击，所以旋钮单击最多会等待约 0.35 秒，S8 的启停仍然立即响应。

## 五、我是怎样一步一步让 AI 帮我完成的

这次我没有一开始就要求 AI 把整个项目重新设计，而是先跑原版，再逐步提出需求。过程中比较关键的提示词和想法是：

1. “你先跑原版吧，把原版跑通来再说。”
2. “在网页 BPM 控制旁增加三个快捷速度按钮：慢速练习 90 / 原版 120 / 快速节奏 140。”
3. “双击进入选择模式，旋转时播报慢速、原版、快速，短按后切换到这个档位。”
4. “旋钮长按 5 秒后，可以选择 EasyInput 模式或鼓机模式。”
5. “能不能不要 Wi-Fi 配网，直接让电脑通过蓝牙连接鼓机？”
6. “不要设备配网码，改成只有按住开发板上的按键，才允许新电脑连接。”

每一步都是先说明我想解决的问题，再让 AI 检查现有代码、修改、测试，最后由我在实物上确认效果。遇到问题时，我会描述真实现象，例如“有声音但是网页按键不亮”，而不是只说“不能用”。这样更容易定位到底是板端、网页还是连接链路出了问题。

## 六、进一步扩展：保留 EasyInput 键盘模式

完成速度档位以后，我又想到：这块板子原来还是一台 EasyInput 键盘。如果每次在鼓机和键盘之间切换都要重新烧录，会比较麻烦。

因此我继续增加了一个双模式选择功能：

- 持续按住旋钮 5 秒，进入整机模式选择；
- 旋转旋钮，在“鼓机模式”和“EasyInput 模式”之间选择，并由板子播报名称；
- 短按旋钮确认，设备重启后进入对应模式；
- EasyInput 原有的 Windows/macOS 选择仍然保留：按住 3～5 秒后松开，再通过第 1、2 键选择系统；
- 模式切换只改变下次启动的应用，不会覆盖原有按键配置。

我在实物上完成了鼓机模式到 EasyInput 模式、再返回鼓机模式的双向验证。进入 EasyInput 后，软件能够识别 USB 键盘，八个按键和旋钮均可以正常使用。

这个扩展不是替换原版鼓机，而是让同一块硬件保留原来的键盘用途。以后如果增加更多应用，也可以继续扩展这个模式选择表。

## 七、进一步扩展：直接蓝牙连接网页

在完成鼓机和键盘双模式以后，我又遇到一个实际使用问题：电脑端原来只能通过 USB Serial 连接开发板。中间曾经尝试过“蓝牙只负责给开发板配置 2.4 GHz Wi-Fi，再通过网络使用”的路线，但实际操作需要选择网络、输入 Wi-Fi 密码和设备配网码，换路由器时还要重新配置，步骤仍然太多。

因此 1.0 网页版最终改成更直接的方案：电脑通过 BLE 直接与鼓机交换状态和控制命令，不再让开发板加入路由器，也不再显示 Wi-Fi 配网页面。这样电脑原来的 Wi-Fi 不会被占用，网页也不需要知道家庭网络密码。

新的首次连接流程是：

1. 先让鼓机停止播放；
2. 按住开发板 S7 三秒，蓝灯常亮，设备开放 60 秒新浏览器登记窗口；
3. 在网页点击“蓝牙连接”，选择 `EasyInput Beatbox`；
4. 网页自动生成随机 client id 和 key，登记到 Beatbox 自己的三槽应用信任表；
5. 后续网页会优先尝试重连已经授权过的设备，不再输入配网码；
6. USB Serial 仍然作为备用连接、烧录和故障恢复通道。

为了避免陌生浏览器随时连接，固件只在实体 S7 登记窗口打开时接受新凭据，最多保存三份。每次连接时，开发板都会生成新的随机数，浏览器用已保存的 key 计算 HMAC-SHA256 答案，认证通过后才可以发送鼓机命令。这个信任表只属于 Beatbox，不主动清除 EasyInput 键盘模式原来的 BLE HID bond。S7 的原鼓机操作也被保留：停止时短按仍切换 A/B，播放时长按仍触发 Fill；只有“停止并按住三秒”才进入新浏览器登记。

这套方案是应用层的“实体授权 + 挑战应答”，不是 Windows 蓝牙系统配对。新随机 challenge 可以防止直接重放以前的认证答案，但目前的登记 key 和普通鼓机命令没有加密，不能写成“已完成 BLE 链路加密”。

BLE 每个数据包较小，所以程序在 JSON 消息外增加了分片头和顺序号；网页重组完成以后，再交给与 USB 相同的协议处理器。这样按键亮起、BPM、A/B、Fill、播放位置和 Pattern 编辑不需要维护两套业务逻辑。

## 九、遇到的真实问题与解决过程

### 问题 1：烧录成功后没有立即运行

刚开始烧录后，板子没有马上进入应用。原因是它还停留在下载状态。解决办法不是继续重复烧录，而是先关机，再重新开机。重新上电后应用才正常启动。

### 问题 2：网页连接失败或重复打开串口

网页曾出现：

`Failed to execute 'open' on 'SerialPort': A call to open() is already in progress.`

这说明自动重连和手动连接可能同时调用了串口打开操作。后来在网页连接层增加了“同一时间只允许一个打开过程”的保护，避免重复调用。

### 问题 3：板子有声音，但网页按键过一会儿不亮

这个问题最容易误判成鼓机坏了。实际现象是：实体按键仍然有声音，说明板端输入和音频没有停止；只有网页不再更新，并显示延迟。检查串口后发现，ESP32-S3 的 USB Serial/JTAG 需要网页明确保持 DTR 信号。

修复时做了三件事：

1. 连接成功后明确设置 DTR 开启、RTS 关闭，避免意外复位；
2. 一段时间收不到状态时，重新设置串口信号并发送 ping；
3. 恢复失败时关闭旧连接，再自动重连。

修改后重新连接测试，八个按键都能持续在网页上正常亮起。这个过程让我体会到：排查问题时，要先看“声音、灯、网页、串口”中哪一层还在工作，不能看到网页不动就直接重新烧录。

### 问题 4：S7 能切换声音，但网页仍显示 Pattern A

在后续验收中，我先发现 S7 长按可以正常加花，但短按不能可靠切换 A/B。检查后，在固件中补充了 S7 的独立消抖和按下、松开事件，并让短按立即应用 A/B 档位；长按仍然保留 Fill 加花功能。重新烧录后，实际声音已经可以从 A 切到 B，说明板端切换成功，但网页仍停留在 `PATTERN A`。

继续检查发现，这次不是固件没有发送状态，而是浏览器还加载着旧版网页代码。浏览器中的页面来自 9 月 4 日，而 A/B 同步修复是在 9 月 8 日写入；同时 Vite 的热更新连接失败，所以页面没有自动换成最新版。

最终的处理过程是：

1. 先断开旧网页占用的串口；
2. 重新启动当前项目的 Vite 网页服务；
3. 打开最新版页面，并重新连接 EasyInput；
4. 再次进行 S7 的 A→B、B→A 和长按 Fill 三项实物测试。

最终三项测试全部正常：声音会随 A/B 档位改变，网页上的 `PATTERN A` / `PATTERN B` 也会同步更新，长按加花仍然有效。这次排查说明，遇到“板子已经变化、网页却没变化”时，除了检查串口协议，也要确认浏览器实际运行的是不是最新代码。

### 问题 5：Wi-Fi 配网虽然可行，但操作仍然太复杂

早期方案能够通过 BLE 把 2.4 GHz Wi-Fi 信息交给开发板，但用户仍要理解“蓝牙配网”和“Wi-Fi 控制”的区别，还要处理设备配网码、网络密码、换路由器和旧凭据恢复。技术上可行不等于上手简单。

最终 1.0 版本取消了这条路线，直接让网页通过 BLE 控制鼓机。为了同时保证方便和基本访问控制，我把设备配网码替换成实体动作：只有停止播放并按住 S7 三秒，才允许新浏览器在接下来 60 秒内登记随机凭据。这样既少输一组密码，又能确认操作者就在开发板旁边。

### 问题 6：新固件写入成功，但设备仍然运行旧版本

一次更新固件时，新镜像已经写入 `0x430000` 的 `beatbox / ota_0` 分区，写入哈希和逐字节回验都成功，但设备重启后仍然返回旧协议能力。这说明写入成功不等于新镜像已经被启动。

只读检查开发板分区表后，确认 `factory` 位于 `0x10000`、`beatbox / ota_0` 位于 `0x430000`，布局本身正确；继续读取 `0x630000` 的两个 OTA 选择扇区，发现它们全部是空白 `FF`。因此启动器按照回退规则继续启动 `factory` 中的旧镜像。

最后使用 ESP-IDF 官方 `otatool`，只把启动选择切换到 `beatbox / ota_0`，没有重写原厂分区、NVS 或声音资源。设备复位后，串口 `hello` 能力和版本发生更新，并正常返回 `state` 和三个 Pattern 数据，说明新固件已经真正运行。这个问题让我进一步理解了：镜像写到哪个地址、启动器选择哪个分区，是两件不同的事。

### 问题 7：网页能选到蓝牙，但 Windows 没有自动完成配对

最开始的直连 BLE 方案要求 GATT 写特征必须加密，希望 Chrome 第一次写入时由 Windows 自动发起配对。我先后做了“固件主动发起”、“延时 300 ms 发起”和“Windows 主导”三个版本。

白盒日志显示，浏览器已经完成设备选择、GATT 连接、服务发现和通知订阅，但加密写在 12 秒内连续 28 次返回 `GATT Error: Not paired`。同时开发板端没有收到 `REPEAT_PAIRING` 或 `ENC_CHANGE`，只看到电脑最后主动断开。这些证据排除了“只要再换一个延时就能配对”的猜测。

因此最后不再依赖 Windows 的 OS bonding，而是改为浏览器凭据和一次性 HMAC 挑战。这个改动保留了“只有按住 S7 才允许新电脑”的交互，也避免了输入配网码，但我仍将加密边界如实写在文档中。

## 十、我的收获

这次作业让我真正理解了课程里两句话：

第一句是“分阶段验收，每一步踩实再往下走”。先跑原版，才能判断后面的问题是原项目的问题，还是自己修改造成的。

第二句是“板端守拍，电脑只看”。节拍来自开发板的 I2S 音频时钟，网页负责显示和编辑。即使网页连接暂时出问题，板端也应该继续发声，不能把节拍交给浏览器计时器。

第三句是“技术上可行，不代表用户愿意多走几步”。Wi-Fi 配网能实现无线，但对这个近距离鼓机来说，直接蓝牙更简单。取消配网码以后，也不能取消安全边界，所以我用“停止时按住 S7 三秒”作为实体授权动作。

我也发现，使用 AI 并不是只说一句“帮我做完”。把目标拆成小步骤、描述真实现象、每一步都回到实物验证，得到的结果更可靠，也更容易知道自己到底改了什么。

## 十一、当前边界与下一步

本次已经完成原版运行、三档有声速度改造、双模式切换，以及直连 BLE 的前三轮白盒排错、新 HMAC 方案构建、烧录、上电检查和首次浏览器登记验证，但我不会把没有单独留下证据的项目写成已经完成：

- 本轮还没有录制一段完整的“拔掉 USB 后长时间独立运行”视频；
- 网页 REC 叠录不是这次主要改造点，还需要在成果视频中单独展示完整过程；
- 当前电脑连接使用 BLE GATT 为主、USB Serial 为备用；两者承载 JSON 领域协议，并不是真正的 USB MIDI Class；
- Pattern 的 `save` 目前主要是确认命令，不能把它写成已经验证的断电持久保存；
- 新 HMAC 诊断固件已完成烧录、上电检查、S7 窗口内首次授权和已登记浏览器手动 HMAC 再连接；仍需在实物上验证自动重连、断电重连、窗口外陌生浏览器拒绝和最多三份浏览器凭据的边界；
- 真实硬件长期运行、蓝牙距离和 USB 备用链路稳定性，还可以继续增加测试。

下一步我会先补齐成果视频中的运行证据，再考虑增加更多模式或改进语音菜单，而不是继续堆叠新功能。

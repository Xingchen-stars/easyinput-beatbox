# 蓝牙连接与白盒诊断

## 日常连接

使用支持 Web Bluetooth 的 Chrome / Edge 打开同一个 Beatbox 网站。同一浏览器已经登记过时，网页用原来的本地钥匙完成挑战应答，不需要输入配网码，也不需要在 Windows 设置中进行传统蓝牙配对。

新网站、新浏览器或清除网站数据后，先停止播放并关闭录制，再按住开发板 S7 三秒。蓝灯亮起后，在 60 秒登记窗口内点击“蓝牙连接”，选择 EasyInput Beatbox。USB 可以只用于供电，不必在网页打开“USB 备用”。

## GATT 正在操作的错误

`NetworkError: GATT operation already in progress.` 表示上一笔蓝牙操作还没有结束。设备发来的授权成功通知，有可能比浏览器收到上一笔写入的完成通知更早。不能仅因为收到了授权成功，就立即并行写入 `ping`。

网页修正采用每个连接一条操作队列：连接、服务发现、特征发现、订阅通知和所有写入按顺序执行。一个 JSON 命令即使拆成多个包，也作为整条消息排队，不能与其他命令交叉。断开后取消旧队列，重连建立新队列；操作超时后冻结旧队列并断开，不向仍忙的连接追加命令。关闭连接直接取消监听并断开 GATT，不额外并行调用 `stopNotifications()`。

这是一项网页修正，不需要重新烧录。原 `v1.0.0` / `v1.0.0-backup.1` 标签和固件发布文件保持原样，在线网页分支通过新提交追加修正。自动化时序回归不能代替真实开发板的蓝牙验收。

## 网页证据

网页控制台记录 `[Beatbox BLE]` 开头的蓝牙日志，包括连接阶段、GATT 操作序号、开始/结束和持续时间。USB 使用 `[Beatbox USB]` 前缀，记录串口打开、读取错误、按键、音符以及设备状态的接收值与网页应用值。默认不显示额外诊断面板。

在当前网页的开发者工具 Console 中可查看最近 256 条安全诊断：

```js
window.__beatboxBleDiagnostics
```

它是内存中的诊断快照，刷新网页后重新开始，不是永久日志，也不会自动上传到 GitHub。它不包含浏览器钥匙、授权 proof、挑战随机数或设备标识。需要保存证据时，在刷新前保存这份诊断，或让浏览器日志采集程序持续监听控制台。

本地 Vite 页面增加 `?ble-diag=1` 时，会把安全日志发到本地开发服务器的 `/__beatbox_ble_log`，可在终端查看。GitHub Pages 没有这个日志接收接口；在线页保留控制台和内存日志，不向不存在的接口发请求。

诊断 USB 实体按键时，应由这一个网页持有串口，不再同时启动 Python 或 ESP-IDF 串口监听。打开本地诊断页，点击“USB 备用”，依次按 S1、S5，短按并松开 S7；查看 `serial:protocol:key` 的接收/应用值，以及 `serial:protocol:state` 的 variation 是否改变。出现 `ignored-frame` 仅表示网页收到了一条无法解析的含 JSON 标记的行，记录长度而不保存原始内容；它本身不证明设备、浏览器或哪段代码是故障来源。模拟消息回归通过，也不代替本次实机消息采集。

`serial:read:start` 确认网页进入读取循环；`serial:read:chunk` 与 `serial:probe` 只记录累计接收字节、数据块、完整行与未换行缓冲区长度，不保存原始串口内容。若串口打开且 `serial:write:ok command=ping` 成功，但 `rxBytes` 一直为 0，只能确认浏览器未收到返回字节，不能据此断定是固件坏了、线路坏了或界面渲染坏了。下一步先断开网页 USB，再对同一块板做有界的直接串口比较；比较结束后释放端口，再恢复网页连接。

## 设备侧证据

USB 串口监听与 BLE 可同时使用，但串口监听会占用“USB 备用”需要的同一个 COM 口。串口号必须先确认，不应写死为某块板子的号码。

```powershell
python scripts/capture_beatbox_ble_log.py --port COM3 --timeout 900 --protocol
```

这是有界、被动的 15 分钟监听，不发送烧录或清除命令。`LISTENING` 表示监听已经开启，`CAPTURE_COMPLETE` 表示已经结束。用 Ctrl+C 停止；网页要改用 USB 时必须先停止监听，避免 `Failed to open serial port`。设备的 `ble_diag` 能提供连接、通知订阅、授权和断开事件；只有实际记录覆盖了某次连接，才可据此判断该次故障。

完整验收至少需要：真实 BLE 首次/再次连接、网页状态同步、实体 S1–S8 反馈，以及释放日志串口后的 USB 备用连接。构建通过、模拟 GATT 通过或串口读到正常固件，都不能单独证明这些项目全部通过。

## 2026-10-01 本地 USB 实机结果

释放独立采集程序后，用户在本地诊断页连接 USB、打开鼓机并保持 REC 关闭。实体 S1/S5 的按下/松开消息正确更新网页 `keysDown` 和 `flashing`；S7 短按后，设备与网页 variation 一致经历 B → A → B → A。用户确认“都有亮，也有切换”。这项结论只覆盖该次本地 USB 会话，不等于全键、所有浏览器或长期运行通过。

故障阶段曾出现网页和独立采集均为 0 字节，以及与开发板拔插关联的 Windows USB 描述符错误。恢复后 18 秒独立采集收到 13,528 字节、44 条状态消息，没有解析错误。过程中没有重烧固件、清 NVS 或修改启动分区；具体失效根因仍未确定。新网页快照和恢复资料见 [v1.0.0-usb-whitebox.1](releases/v1.0.0-usb-whitebox1.md)。
